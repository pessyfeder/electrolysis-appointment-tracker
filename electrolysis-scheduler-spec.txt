ELECTROLYSIS APPOINTMENT SCHEDULER - SPEC DOC

Prepared for: Pessy Friedman
Date: September 3, 2026
Status: Draft v7.0 - revised after v6 build feedback (per-date business-
hours overrides replacing weekly-only editing, appointment search, an
auto-fitting calendar that no longer needs a maximized window or
scrolling, automatic no-show detection, and a restyled Admin/Billing/
Client Detail UI)

================================================================

1. OVERVIEW

A desktop application for a solo electrolysis practitioner (Mom) to
manage appointment scheduling, client contact/payment records, and
business-hour enforcement - running entirely locally on one computer,
with no cloud backup and no email/SMS integration.

This document is written to be used by Pessy to build the application.
It defines scope, data model, features, and technical decisions in
enough detail that implementation can begin without further design
work.

================================================================

2. GOALS & NON-GOALS

Goals:
- Replace paper/spreadsheet scheduling with a single desktop app for one
  practitioner.
- Make it fast to book, reschedule, and cancel appointments from a
  calendar view, eliminating issues such as double-booking.
- Keep a simple client database: name, phone, and payment history.
- Track payments per appointment/client so Mom can see what's owed or
  been paid (including credits/debts carried across visits).
- Enforce business hours and appointment length limits, and prevent
  appointments from leaving an unbookable gap in the schedule. There's
  no separate "buffer time" concept to build - since the minimum
  appointment length is 15 minutes, any gap of 1-14 minutes between
  appointments is simply dead time nothing could ever fill, so the app
  just needs to disallow gaps in that 1-14 minute range (appointments
  can be back-to-back with a 0-minute gap, or spaced 15+ minutes apart).
- Let Mom (Admin) block off time slots or full days when unavailable.
- Allow more than one client to share a single calendar slot (e.g. a
  parent and child booked together), while still billing each of them
  separately based on their own actual time (see 7.1 and 7.3).
- Keep past dates from being booked by mistake - they're grayed out and
  not clickable for new appointments, while Admin can still view who was
  booked on them.

Non-Goals (out of scope for v1):
- Multi-practitioner or multi-location support.
- Online client self-booking (client-facing web portal).
- Full clinical/EMR-grade treatment charting (body maps, photos) - can
  be a future phase.
- Mobile app version.
- Insurance billing/claims.
- Email or SMS reminders/notifications of any kind.
- Cloud backup or cloud sync of any kind - data lives only on the local
  machine.

================================================================

3. TARGET USER

One person: a solo electrolysis practitioner (Mom) who both performs
treatments and manages her own front-desk work (scheduling, billing).
She needs the app to be simple, reliable, and low-maintenance - not an
enterprise practice-management system.

================================================================

4. TECH STACK

Language: Python 3.13 (embedded interpreter bundled with the app - see
  4. Packaging below; Mom doesn't need Python installed separately)

GUI framework: PySide6 (Qt for Python)
  Recommended over Tkinter/Kivy - better-looking widgets out of the box
  (calendar view, tables, forms), actively maintained, free (LGPL), good
  for a "real" business app. Tkinter is a fallback if a lighter
  dependency footprint is preferred; Kivy is not recommended
  (touch/mobile-oriented, not ideal for dense forms/tables).

Local database: SQLite (via sqlite3 or SQLAlchemy)
  Single-file DB, zero server setup, perfect for single-user local
  storage.

Packaging: PyInstaller
  Builds a standalone .exe/.app so Mom doesn't need Python installed.

Not used in this build: email sending, SMS sending, cloud backup/sync.
The app has no internet dependency - it is a fully offline, local-only
tool.

================================================================

5. ARCHITECTURE OVERVIEW

Single-process desktop app, fully local, no network calls:

  PySide6 GUI
  (Calendar | Clients | Billing)
        |
  App Core Logic (Python services)
  (booking rules, business-hour/gap validation, price calculation,
   balance tracking, password gate)
        |
  SQLite (local DB only - no backup job, no external sync)

Note: the database is local-only. There is no server, no login over a
network, and no outbound network traffic of any kind - everything the
app does happens on the one machine it's installed on.

6. DATA MODEL

SQLite schema (v3):

--- Table: clients ---
  id            INTEGER PK
  first_name    TEXT      optional
  last_name     TEXT      required
  phone         TEXT      required - stored/displayed formatted as
                           (XXX) XXX-XXXX
  notes         TEXT      optional free-text, not part of the normal
                           add/edit-client flow (no notes prompt when
                           saving a client) - left in the schema for any
                           future use, but the client form no longer
                           shows a notes field
  created_at    DATETIME
  archived      BOOLEAN   soft-delete flag instead of hard delete

--- Table: appointments ---
  An appointment is a booked calendar slot (a time block). It no longer
  belongs to a single client directly - one or more clients can be
  attached to the same slot via appointment_clients below, so e.g. a
  parent and child can share one slot on the calendar while still being
  treated - and billed - one at a time, sequentially (see 7.3).
  id                INTEGER PK
  start_datetime    DATETIME  required
  end_datetime      DATETIME  required (start + duration)
  notes             TEXT      optional (appointment-level note, e.g.
                               treatment area for this visit)
  created_at        DATETIME

--- Table: appointment_clients ---
  Join table: one row per client attached to an appointment. Each
  client's own session is tracked independently so a shared slot can be
  billed one person at a time.
  id                  INTEGER PK
  appointment_id      INTEGER   FK -> appointments.id
  client_id           INTEGER   FK -> clients.id
  order_index         INTEGER   position in the sequence clients are
                                 treated (0 = first)
  status              TEXT      scheduled / in_process / completed /
                                 cancelled / no_show - this client's own
                                 status on the shared appointment
  session_started_at  DATETIME  set when this client's session is
                                 started
  price               DECIMAL   auto-calculated for this client only,
                                 not manually entered - see 7.3 for
                                 formula

--- Table: payments ---
  id                INTEGER PK
  client_id         INTEGER   FK -> clients.id
  appointment_id    INTEGER   FK -> appointments.id, nullable (payments
                               aren't always tied 1:1 to an appointment -
                               clients can pay in bulk ahead of time or
                               pay later, building up a credit or a debt)
  amount            DECIMAL   required
  method            TEXT      cash / card / check / other
  paid_at           DATETIME
  notes             TEXT      optional

--- Table: blocked_times ---
  id                INTEGER PK
  start_datetime    DATETIME  required
  end_datetime      DATETIME  required (can span a full day)
  reason            TEXT      required free-text note on why Mom is
                               unavailable
  created_at        DATETIME

--- Table: business_hours ---
  id                INTEGER PK
  day_of_week       TEXT      Sun / Mon / Tue / Wed / Thu / Fri / Sat
  start_time        TIME
  end_time          TIME
  Note: a given day can have more than one row if there are separate
  morning and evening blocks; a day with no rows is closed (see 7.1 for
  the actual hours).

--- Table: business_hours_overrides ---
  A per-date override of the recurring weekly schedule in business_hours
  above - added so Admin can adjust hours for one specific date (a
  shortened evening, a one-off early close) without touching every future
  occurrence of that weekday. A date with no rows here simply uses its
  normal weekday hours; a date overridden to be fully closed still gets
  exactly one row, with start_time/end_time both NULL, so "closed" can be
  told apart from "no override at all." See 7.1 and 7.4/8 (Edit Business
  Hours).
  id            INTEGER PK
  date          TEXT      required, ISO date (YYYY-MM-DD)
  start_time    TIME      nullable (NULL only in the single-row "fully
                           closed" case above)
  end_time      TIME      nullable (same)

--- Table: settings ---
  key       TEXT PK   e.g. admin_password_hash
  value     TEXT

7. FUNCTIONAL REQUIREMENTS

7.1 Calendar & Appointment Booking
- Main screen shows a calendar with a Day / Week / Month toggle (default:
  week view - it shows fuller, color-coded appointment cards with the
  client's status right on them, vs. month view's compact time+name
  chips). Day view shows a single day's business-hours blocks as a wide
  time grid, with a plain, always-readable list of that day's
  appointments (time, client, status) alongside it - useful once a day
  gets busy enough that week view's narrower columns get cramped.
- Alongside Day/Week/Month, a "Today / Go to Date" toggle lets Admin jump
  the calendar straight to any date via a popup calendar picker (Go to
  Date), not just step forward/back or return to today - the current view
  mode (day/week/month) is kept, only the anchor date moves. Whichever
  side matches the calendar's current date is shown as active.
- A "Search Appointment" button finds an appointment by client name/phone
  and/or an exact date and jumps straight to it (opens Day view on that
  date with the appointment's own dialog open), rather than requiring
  Admin to scrub through the calendar to find one client's booking.
- Clicking a day on the month grid jumps to the day view for that date.
  Past days are grayed out and their empty time is not clickable - you
  can't create a new appointment on a date that's already gone. Existing
  appointments already booked on a past day remain fully clickable so
  Admin can view which client(s) were booked and their contact info; only
  creating new bookings on past dates is blocked.
- On today specifically, each business-hours time block grays out on its
  own once that block's end time has passed, rather than waiting for the
  whole day to end - e.g. a 10:30am-1:30pm block reads as done by 9pm
  even though a 7:30-10:30pm block on the same day hasn't ended yet.
  Within a block that's still open, the already-elapsed portion of it
  (from the block's start up to right now) grays out on its own too, in
  Day/Week view's time grid, rather than the whole block staying
  full-brightness right up until it ends - since that already-elapsed
  time is just as unbookable as a fully-past block. This only affects the
  visual cue and whether new bookings can be made in that block/time; an
  appointment already sitting in a grayed block or grayed portion stays
  fully clickable, and Start/End Session (7.3) for a client on today's
  schedule remains available no matter what time it currently is.
- Click an open time slot in the week or day view to create a new
  appointment; select an existing client, quick-add a new one inline, or
  attach more than one client to the same slot (see "Multiple clients
  per appointment" below).
- Appointment form fields: one or more clients, date/time, duration (or
  end time), appointment notes (optional), status (per client - see
  below). Price is calculated automatically per client (7.3), not typed
  in. Required fields are marked with "*" (with a "* Required" legend on
  the form); fields that aren't required say so in their label, e.g.
  "Notes (optional)" - never both a label and a placeholder saying the
  same thing.
    - Clicking anywhere on the date field (not just its small calendar
      icon) pops up the calendar picker. Dates before today are grayed
      out and can't be selected - whenever the date is still editable,
      not just for a brand-new appointment (see the "locked once started"
      rule below - a reschedule of a not-yet-started future appointment
      is still subject to this same past-date lockout).
    - The start time is never typed in. Clicking the start-time field
      opens a dropdown listing every start time, in 5-minute intervals,
      on the selected date where a booking is actually possible -
      respecting business hours (including any per-date override, see
      below), existing appointments, and the gap rule below - with the
      earliest one marked. Times are grouped under non-selectable
      "Morning Appointments" / "Evening Appointments" headings, each
      labeled with that block's actual hours for the selected date (e.g.
      "Evening Appointments (7:30 PM - 10:30 PM)"), rather than shown as
      one flat list. Picking an entry displays it in the field; that's
      the only way to set it.
    - Duration is chosen from a list of valid options in 5-minute steps,
      starting at 15 minutes and going up to (business-hours block end
      time - appointment start time). The list automatically excludes any
      duration that would overlap the next appointment or leave an
      unbookable 1-14 minute gap before it (see the gap rule below), so
      it's not possible to pick an invalid duration in the first place.
      Durations of an hour or longer display as e.g. "1 hour 15 minutes"
      rather than "75 min".
- Multiple clients per appointment: a single calendar slot can have more
  than one client attached (e.g. a parent and child booked together).
  They are still treated - and billed - one at a time: Start Session on
  one client's row begins timing just that client; End Session bills
  just that client for their actual time (7.3) and, if another client is
  still waiting on the same appointment, the app asks whether to start
  that next client's session right away. Each client on a shared
  appointment can independently be marked no-show or cancelled without
  affecting the others.
- Edit-in-place to reschedule (only while nothing on the appointment has
  started yet - see below).
- Cancel/no-show marking without deleting the record (per-client status
  change, kept for history).
- Conflict warning if a new appointment overlaps an existing one, a
  blocked time, or falls outside business hours.
- Week view clearly shows gaps for finding open slots, and past days are
  visually grayed out (see above).
- Appointments are color-coded by status (scheduled / in progress /
  completed / cancelled / no-show); a shared appointment with clients in
  different states shows the most relevant color (in-progress and
  scheduled take priority over finished/cancelled states). Inside the
  appointment form, each client's own row is likewise color-coded to
  match their status and labels it in text (e.g. "Completed - $37.50"),
  updating immediately when the status changes - not only after the form
  is reopened.
- App auto-suggests the next available slot / a gap between two booked
  slots by flashing it.
- Successfully scheduling or rescheduling an appointment shows a brief
  confirmation "ticket" (client name(s), date, time, and notes) as a
  final on-screen recap before the form closes.
- A client left "Scheduled" on an appointment whose business-hours block
  has already ended, without their session ever having been started, is
  automatically promoted to "No-Show" the next time appointment data is
  displayed - Admin doesn't have to notice a missed appointment and flip
  its status by hand.
- Once any client on an appointment has actually started their session
  (or the appointment's start time has passed), its date/time/duration
  can no longer be changed - only status actions and adding/managing
  clients remain available, so a billed session's timing can't be
  retroactively altered.


  Business hours (default, stored in the business_hours table so they
  can be adjusted without a code change):
    Sun: 11:30 - 1:30, 7:30 pm - 10:30 pm
    Tue: 7:30 pm - 10:30 pm
    Mon, Wed, Thu: 10:30 am - 1:30 pm and 7:30 pm - 10:30 pm
    Fri, Sat: closed (no appointments)

  These are the recurring weekly hours. Admin can additionally override
  the hours for one specific date (business_hours_overrides, see 6 and
  7.4/8) - e.g. closing early on one particular evening - without
  changing every other occurrence of that weekday; a date with no
  override just uses the weekly schedule above.

  Scheduling rules (enforced by the app, not just suggested):
    - Appointment length must be at least 15 minutes, and at most the
      time remaining between the requested start time and the end of
      that business-hours block (e.g. an appointment starting at
      9:00 pm in the evening block can be at most 30 minutes).
    - No separate "buffer" is needed between appointments - back-to-back
      appointments (0-minute gap) are fine. What's not allowed is a gap
      of 1-14 minutes between the end of one appointment and the start
      of the next, since that space is too short for the 15-minute
      minimum appointment length to ever fill it. A gap is only valid
      if it's 0 minutes (back-to-back) or 15+ minutes. This same rule
      also applies against a business-hours block's own open/close time:
      a start time that would leave a 1-14 minute idle gap right after
      the block opens, or a duration that would leave one right before
      the block closes, is likewise excluded from the start-time/
      duration options offered - so this is enforced entirely by keeping
      such choices out of those lists in the first place, never by
      rejecting a choice after it's already been offered and picked.
    - Appointments cannot be booked inside a blocked time slot/day.

  Blocking time off:
    - Admin (Mom) can click on the calendar to block off a specific
      time slot or an entire day.
    - A blocked slot/day requires a short note explaining the reason
      for unavailability - this is a required field, not optional, so
      there's always a record of why a slot was blocked.
    - Blocked time behaves like a hard conflict - no appointment can be
      booked over it until it's removed.

7.2 Client Database
- Client list, searchable/filterable by name or phone.
- Client detail view: contact info (name, phone), full appointment
  history, full payment history, running balance (charged minus paid -
  positive means the client owes money, negative means the client has a
  credit toward future visits).
- Add/edit/archive clients (archive instead of hard delete, to preserve
  appointment/payment history integrity).
- Add/edit-client form only asks for last name (required), first name
  (optional), and phone (required, validated as a 10-digit number and
  auto-formatted as (XXX) XXX-XXXX). There is no notes field in this
  form - saving a client's info never prompts for notes.

7.3 Billing & Payments
- No formal "packages" - billing is purely time-based.
- Appointment price is auto-calculated and displayed upon session
  completion (NOT when the appointment is booked), using:
  price = session_length_minutes x 2.5 (i.e. $2.50 per minute). This
  rate is uniform across every treatment area/type - there is no
  per-area pricing.
- Record a payment against a client (optionally tied to a specific
  appointment). Clients may pay in bulk ahead of time (building a
  credit that future appointment charges draw down) or pay later
  (building a debt/balance owed) - both are just reflected in the
  running balance, not tracked as a formal "package."
- Track running balance per client (total charged vs. total paid).
- Simple report/export: payments received in a date range (for
  tax/bookkeeping purposes) - CSV export at minimum.
- Click Start Session / End Session on a client's row - times that
  client's session, calculates time x rate, displays amount owed at the
  end of the session based on actual time worked, not based on time
  scheduled. Both actions require re-entering the Admin password first
  (same extra confirmation as editing business hours/blocked time, see
  7.4) - this guards against an accidental tap starting the wrong
  client's billing clock, or ending one early. Booking a new appointment,
  rescheduling, and cancelling are NOT gated - only starting/ending a
  session is.
    - That client's status becomes "In Progress" once Start Session is
      clicked (and the password confirmed), remaining so until End
      Session is clicked (again password-confirmed), at which point
      their status becomes "Completed" and their price is calculated and
      shown.
    - When an appointment has more than one client attached to the same
      slot (7.1), each client is billed independently and sequentially:
      Start/End Session only ever times one client at a time. When one
      client's session ends, if another client is still waiting on that
      same appointment, the app asks whether to start that next client's
      session immediately - their time is tracked separately and they
      are billed separately based on their own actual session length.

7.4 Admin Access
- The app requires the Admin password (Mom's password) to open/launch
  at all - it cannot be used without entering it first.
- Edit Business Hours (in the Admin tab) edits one specific date at a
  time, not a whole recurring weekday - picking a date loads its
  currently-effective hours (an existing override for that date, or
  otherwise that weekday's normal schedule as an editable starting
  point), and Save records an override for that date only, leaving every
  other date - including every other occurrence of that same weekday -
  on the normal weekly schedule. "Reset to Default Hours" removes the
  date's override entirely, reverting it back to that weekday's normal
  hours. Saving is blocked, with a listing of the conflicting
  appointment(s), if any of that one date's existing bookings would no
  longer fit the proposed hours - they must be rescheduled or cancelled
  first, same as before, just scoped to that single date instead of
  scanning every future date for conflicts.
- Once the app is open, no further password is needed for routine use:
  creating, rescheduling, or cancelling appointments; entering client
  info; and recording payments.
- Switching from the Appointments tab into the Admin tab (7.4/8 - Edit
  Business Hours, Block Time Off, and Billing all live there) requires
  re-entering the Admin password as an extra confirmation step, separate
  from the one used to open the app. The prompt appears - and the tab
  switch either happens or doesn't - before any Admin content becomes
  visible, so a wrong or cancelled password never flashes the screen
  before reverting. Because reaching Edit Business Hours or Block Time
  Off now requires having already cleared this gate to get into the
  Admin tab in the first place, saving changes on either of those two
  screens doesn't re-prompt a second time.
- Right-clicking a specific slot directly on the calendar to block it off
  is a separate, still-live shortcut that doesn't go through the Admin
  tab - it keeps its own password prompt each time, since it's reachable
  without ever entering Admin.
- Starting or ending a client's session (Start Session / End Session,
  see 7.3) requires that same extra password confirmation, since it
  starts/stops the billing clock and locks in the charged price -
  mistakes there are harder to walk back than a booking mistake.
- Store only a hash of the password locally (e.g. via bcrypt or a
  similar library) - never store or log the plaintext password.

7.5 Data Storage
- All data lives in a single local SQLite file on the practitioner's
  computer. There is no cloud backup, no cloud sync, and no automatic
  export - this was explicitly descoped for v1.
- Because there's no backup, it's worth calling out as a risk: if the
  computer's disk fails or the file is deleted, the data is gone. If
  that risk becomes a concern later, manual backup (e.g. periodically
  copying the database file to a USB drive) is a lightweight option
  that doesn't require any of the cloud infrastructure this version
  intentionally skips.

8. UI/UX REQUIREMENTS

The app has two top-level tabs: Appointments and Admin. Admin requires
re-entering the Admin password to switch into (see 7.4).

Screens:
1. Appointments (Calendar/Dashboard) - Day / Week / Month toggle (week
   view by default on launch - see 7.1), a "Today / Go to Date" toggle
   and a "Search Appointment" button for jumping to a date or a specific
   client's booking, a "Schedule Appointment" button, quick view of the
   current schedule, and the ability to block off a specific slot
   directly on the calendar via right-click. Past dates are grayed out
   and not clickable for new bookings, but existing appointments on them
   stay clickable so Admin can view who was booked; on today, each
   business-hours block - and the already-elapsed portion within a block
   still open - grays out individually once it has ended/elapsed (see
   7.1). The Day/Week time grid always shows the full business-hours
   schedule without needing to scroll, scaling itself to fit whatever
   height is actually available on screen.
2. Clients - searchable list + detail panel (contact info, history,
   balance).
	- Client panel should pop up during booking process; not be displayed
	  separately. Popups opened from within a form (adding/picking a
	  client, editing info) open centered over that form rather than
	  wherever the OS would otherwise place them.
3. Appointment form (modal or side panel) - create/edit an appointment
   with one or more clients attached (shows each client's
   auto-calculated price once their session completes, color-coded and
   labeled by status). Clicking the date field pops up a calendar
   picker (past dates grayed out); clicking the start-time field opens a
   dropdown of every permissible 5-minute-interval time - there's no
   typed entry for either; duration is picked from a pre-validated list
   of options (see 7.1). Starting or ending a client's session prompts
   for the Admin password (see 7.3/7.4). A successful create/reschedule
   shows a confirmation "ticket" recapping the client(s), date, time,
   and notes.
4. Admin - a segmented sub-tab strip (Edit Business Hours / Block Time
   Off / Billing) that opens on Edit Business Hours by default;
   switching between the three swaps the content in place rather than
   opening separate dialogs or pages. Edit Business Hours picks a date
   and edits that date's hours only, with a "Reset to Default Hours"
   option to drop back to its normal weekly schedule (see 7.4); Save/
   Cancel on both Edit Business Hours and Block Time Off start disabled
   and only become active once a field has actually been changed, so
   there's nothing to accidentally save or discard before then. Billing
   and Client Detail (opened from a Billing balance row) present their
   content in rounded card panels rather than plain native-OS group
   boxes, with balances/credits color-coded (red = owed, green = credit)
   consistently in both places. Billing records payments, shows client
   balances, and exports reports (see 7.3). Reaching this tab at all
   requires the Admin password (see 7.4).

General UX notes:
- Should feel like a lightweight, single-purpose business tool - fast
  to open, fast to add an appointment, minimal clicks for the most
  common action (booking a new appointment for an existing client).
- The Admin password is prompted once at launch to open the app at all
  (see 7.4). A second password prompt appears when switching into the
  Admin tab (which holds Edit Business Hours, Block Time Off, and
  Billing), when right-clicking to block off a specific calendar slot
  directly, or when starting/ending a client's session (7.3) - routine
  booking, rescheduling, cancelling, client entry, and payment recording
  don't require re-entering it.
- The main window and the scheduling-confirmation ticket popup use a
  custom-drawn title bar (drag to move, minimize/maximize/close, still
  resizable from the window's edges) instead of the operating system's
  native one, so their appearance doesn't depend on the OS's window
  theme or accent color. The app launches as a normal, centered window
  sized around its content rather than maximized - the Day/Week
  calendar grid scales its own layout to fit whatever height it's
  actually given (see Screen 1 above), so there's no longer a reason to
  force the window to cover the whole screen on launch, and the window
  remains freely resizable afterward.
- Clear visual distinction between appointment statuses (scheduled /
  in process / completed / cancelled / no-show) via color coding, both
  on the calendar and on each client's row within the appointment form.
  Appointment text on the calendar is drawn at one fixed, consistently
  legible size and truncated to fit a card's available space, rather
  than being shrunk smaller to cram more text in; overlapping
  appointments sharing a slot are sized so a short one is never
  squeezed down to unreadable, borrowing room from its longer neighbors
  as needed.
- Blocked time should be visually distinct from booked appointments on
  the calendar (a plain bordered box exactly bounding the blocked span,
  labeled with its reason). Past dates use a separate grayed-out
  treatment to signal "view only, not bookable" - both on the month/
  week calendar and in the appointment form's date picker.
- Every form marks which fields are required ("*", shown in red, with a
  legend) vs. optional (stated once, in the field's label) - never left
  ambiguous, and never stated as optional in two places at once.

9. NON-FUNCTIONAL REQUIREMENTS

- Reliability: the app must not lose data on crash - write to SQLite
  with transactions; auto-save rather than requiring an explicit "save"
  step. The packaged build runs windowed (no console window on
  Windows), so an unhandled error is caught, appended to a local
  error.log file (in the same app-data folder as the database), and
  shown to Mom in a dialog - rather than the app silently doing nothing,
  which is otherwise indistinguishable from a bug that just doesn't
  work.
- Performance: should feel instant for a single-user dataset (expected
  to be at most a few thousand clients/appointments) - no meaningful
  performance engineering required at this scale.
- Privacy/security: client contact and payment info is sensitive. At
  minimum: store the DB file in the user's local app-data directory
  (not a shared folder), avoid printing sensitive data to logs, and
  store the Admin password only as a hash (7.4), never in plaintext.
  The password is required just to open the app, so a lost/forgotten
  password effectively locks Mom out - worth planning a simple recovery
  path (e.g. a documented reset procedure) during development.
- Portability: package as a standalone executable (PyInstaller) so it
  runs without a separate Python install.
- Connectivity: the app is fully offline by design - no feature depends
  on an internet connection.

10. BUILD PHASES

Phase 1 - MVP
- Admin password gate to open the app
- Calendar view + appointment CRUD
- Business-hours, appointment-length, and unbookable-gap validation
- Client database (last name required, first name optional, phone)
- Auto-calculated appointment pricing ($2.50/minute)
- Local SQLite storage

Phase 2 - Billing & Admin Controls
- Payment tracking + running client balance (credits/debts)
- CSV export of payments
- Second password gate specifically for editing time availability
  (business hours changes, blocking/unblocking time)
- Block off time slots/full days with a required reason note

Phase 3 - Polish & Optional Enhancements
- In-app editing of business hours (instead of only via direct DB/config
  edits)
- Refined status color coding and calendar visuals
- Manual local backup helper (e.g. a "copy database file to..." button),
  if the no-backup risk noted in 7.5 becomes a concern later

Phase 4 - Multi-Client Appointments & Scheduling UX
- Simplified client form: last name only required, phone auto-formatted,
  no notes prompt
- Past dates grayed out and locked from new bookings, while remaining
  viewable for Admin
- Dropped the separate day view - month and week only (reintroduced in
  Phase 6 below once appointment volume made a day-at-a-time view
  genuinely useful again)
- Appointments can have more than one client attached to the same slot,
  each billed independently and sequentially (Start/End Session per
  client, with an auto-suggested "start the next client" prompt)
- Appointment form: click-to-suggest start time (superseded by the
  click-only dropdown in Phase 5 below), a pre-validated duration list,
  and a date picker that won't allow picking a past date for a new
  appointment

Phase 5 - Scheduling UX Refinements & Session Safeguards
- Start-time field redesigned as a click-only dropdown listing every
  permissible 5-minute-interval time on the selected date, replacing the
  old "auto-fills the earliest time, still editable by typing" behavior
  - there is no way to type a start time anymore
- Date field opens its calendar picker on a click anywhere in the field
  (not just the small icon), and the past-date lockout now applies
  whenever the date is editable, not only for brand-new appointments
- Start Session / End Session gated behind the Admin password (7.3/7.4),
  to prevent an accidental tap from starting/ending the wrong client's
  billed session
- Required vs. optional fields marked consistently across all forms
  ("*" + legend for required; stated once, in the label, for optional)
- Durations of an hour or more display as "x hour(s) x minutes" instead
  of raw minutes
- Per-client session rows inside the appointment form are color-coded to
  match their status, in addition to already showing the status as text,
  and now update immediately (not only after reopening the form)
- Default calendar view on launch changed from month to week, since week
  view's fuller appointment cards read as more "finished" than month
  view's compact chips
- Record Payment: the client dropdown is now resolved by matching its
  actual selected/typed text, instead of trusting whatever was last
  selected - previously, typing a name to filter the list without
  clicking a suggestion could silently record the payment against the
  wrong (previously-selected) client
- Unhandled errors are now caught, logged, and shown in a dialog instead
  of failing silently (see Non-Functional Requirements)

Phase 6 - Day View, Admin Hub & Window Chrome
- Reintroduced a Day view (Day / Week / Month toggle) - a single day's
  business-hours blocks as a wide time grid, alongside a plain, always-
  readable list of that day's appointments (time, client, status);
  supersedes Phase 4's decision to drop it, since a day-at-a-time view
  proved genuinely useful once appointment volume grew. Overlapping
  appointments in this view cascade with a wide, readable offset instead
  of being squeezed into equal-width slivers.
- Clicking a date on the month grid now opens the day view for that
  date, rather than the week view
- A day's business-hours time blocks gray out individually once their
  own end time has passed, rather than only once the whole day is in the
  past (see 7.1) - this is a display/new-booking rule only; Start/End
  Session for a client already on today's schedule stays available
  regardless of the time of day
- Billing is no longer its own top-level tab; it now lives inside a new
  Admin tab alongside Edit Business Hours and Block Time Off, presented
  as a segmented sub-tab strip that opens on Edit Business Hours by
  default
- Switching into the Admin tab now requires the Admin password, checked
  before the tab visually changes at all (so a failed/cancelled attempt
  never flashes Admin content on screen). Because that's now the only
  way to reach Edit Business Hours or Block Time Off - their direct
  buttons on the calendar toolbar were removed - saving on either no
  longer separately re-prompts. Right-clicking a calendar slot to block
  it off directly is unaffected and still prompts on its own, since it
  doesn't go through the Admin tab.
- Month view redesigned as a centered, rounded card (rather than a flat
  rectangle stretched to the window's full width) with a clear month/
  year header of its own
- A confirmation "ticket" (client(s), date, time, notes) is shown after
  successfully scheduling or rescheduling an appointment
- Child dialogs opened from within a form (adding/picking a client,
  editing client info) now open centered over their parent instead of
  wherever the OS would otherwise place them
- Main window and the scheduling-confirmation ticket now use a custom-
  drawn title bar (drag to move, minimize/maximize/close, still
  resizable from the window's edges) instead of the native OS one, so
  their appearance doesn't depend on the OS's window theme/accent color
- App launches maximized so its full layout is visible without the user
  needing to resize it
- "Add Appointment" button relabeled "Schedule Appointment"
- Fixed: an editable client-picker dropdown (e.g. "+ Add Client",
  Record Payment's client field) could flash open and immediately close
  again on click instead of staying open to choose from

Phase 7 - Per-Date Hours, Search, Auto-Fit Calendar & UI Polish (this
revision)
- Edit Business Hours reworked to override one specific date at a time
  (business_hours_overrides, see 6) instead of only ever editing a whole
  recurring weekday - picking a date shows its currently-effective hours
  (an override if one exists, else that weekday's normal schedule) as an
  editable starting point, Save records an override for that date only,
  and "Reset to Default Hours" removes the override to revert to the
  normal weekly schedule. Conflict-checking against existing appointments
  is now scoped to just the one date being edited, not a year-long scan.
  Save/Cancel here, and on Block Time Off, start disabled and only
  activate once a field is actually changed, so there's nothing to
  accidentally save or discard before any real edit is made.
- The 1-14 minute unbookable-gap rule (7.1) now also applies against a
  business-hours block's own open/close time, not only against
  neighboring appointments - so a start time or duration that would
  leave that kind of dead time right after opening or right before
  closing is excluded from the offered options the same way one next to
  another appointment already was.
- A client left "Scheduled" past their appointment's end time, without
  ever having been started, is now automatically promoted to "No-Show"
  whenever appointment data is displayed, instead of relying on Admin to
  notice and change it by hand.
- New "Search Appointment" button: find an appointment by client name/
  phone and/or an exact date, then jump straight to it (opens Day view
  on that date with the appointment already open).
- New "Go to Date" toggle next to "Today": opens a calendar popup to jump
  the calendar straight to any date, in whatever view mode is currently
  active, rather than only stepping forward/back or returning to today.
- The app no longer launches maximized - it opens as a normal, centered
  window sized around its content and remains freely resizable. The Day/
  Week time grid now scales its own vertical scale to whatever height is
  actually available, so the full business-hours schedule for the
  visible day(s) always fits without ever needing to scroll, at any
  window size.
- Appointment/blocked-time text on the calendar is now drawn at one
  fixed, consistently legible size and truncated to fit rather than
  shrinking smaller to cram more in; the format is simplified to a
  single "Name: time" line (Day view's wider column shows the full
  start-end range, Week view's narrower columns show just the start
  time). Overlapping appointments sharing a slot now get proportionally-
  sized heights with a readable minimum, so a short appointment
  sandwiched between long ones borrows room from its neighbors instead
  of rendering squeezed unreadably thin.
- Blocked time on the calendar is now shown as a plain bordered box
  exactly around the blocked span (labeled with its reason) instead of
  the previous diagonal-hatch pattern, which read as visually messy.
- The start-time dropdown now groups its options under non-selectable
  "Morning Appointments" / "Evening Appointments" headings, each labeled
  with that block's actual hours for the selected date (reflecting any
  per-date override), instead of one flat list of times.
- Required-field asterisks are now shown in red (both on form labels and
  the "* Required" legend), instead of plain text, for a clearer at-a-
  glance cue.
- Billing and Client Detail are restyled to match, using rounded white
  card panels in place of plain native-OS group boxes; balances/credits
  are consistently color-coded (red = owed, green = credit) in both
  places, and history tables auto-size each column to its content with
  one column (typically Notes) absorbing the remaining width, instead of
  stretching every column evenly.
- Edit Business Hours and Block Time Off now use larger text/controls
  than the rest of the app, since Admin is most likely to be reading
  these forms on a small front-desk screen.
- Clicking a date on the month grid now shows an immediate pressed
  highlight on that cell while the switch to Day view completes a
  moment later, so the jump from a whole month to a single day feels
  less abrupt without the click ever reading as unresponsive.
